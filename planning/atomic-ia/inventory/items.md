# Concept inventory — Items

Domain scope: the Item entity — core fields vs custom fields, the six custom field types,
allowed-values lists and their behavior, the "Allow new values" toggle and its CSV
interaction, reference fields, item Page overrides, and general Item CSV import/export.

Verified against `/workspace/qrtub/src` (primarily `lib/types/field-config.ts`,
`lib/types/semantic-item.ts`, `lib/database/thing-serializer.ts`,
`lib/database/server-item-overrides.ts`, `lib/services/csv-import-export-service.ts`,
`lib/services/csv-row-validation.ts`, `lib/utils/csv-constants.ts`,
`components/blocks/FieldConfigurationManager/FieldConfigurationManagerCompact.tsx`,
`components/blocks/LandingPageEditor/core/EditorProvider.tsx` +
`core/editorReducer.ts`, `lib/utils/duplicate-item.ts`), plus `GLOSSARY.md`. Existing docs
`custom-fields.mdx` and `using-fields.mdx` currently cover a large fraction of this ground in
two big pages — both are candidates for retirement/replacement by this atomic breakdown.

## Inventory

Blank/whitespace-only values are normalized to `null` so they don't collide on the unique constraint. | Items | Item ID | `items/item-id` | Standalone — distinct mechanics (per-Tub uniqueness constraint, whitespace normalization, tie-in to numbered-pattern Link generation) easily clear 150 words, same bar as Linear's `priority.md` (243 words). |
| 4 | Tags | The core `tags` field: an array of string values, multi-select by default, free-form additions allowed by default, rendered as colored chips wherever the Item is shown (including the scanned Page). | Items | Tags | `items/tags` | Standalone — real distinct behavior (array core field + allowed-values colors + default `allowNewValues: true`) separate from the generic "List" custom field type. |

| 6 | Duplicating an Item | The "Copy" action: clones an Item's fields but drops server-generated columns and the Item ID (which would collide on the per-Tub unique constraint), appends "(Copy)" to the name, and does not carry over the source Item's Page override (a fresh `id` has no override row). | Items | Duplicating an Item | `items/duplicating` | Standalone — a distinct, well-defined task with real behavior worth stating explicitly (what carries over, what doesn't, why Item ID resets). |
| 7 | Item Page overrides | The mechanism letting one Item's rendered Page diverge from the Tub's base Page template: an Override toggle (lock/unlock) that auto-enables whenever you open any Item's page in the editor, decides whether Save writes the base template or an item-specific override record, warns before an override-off Save would blast changes onto every Item without its own override, and can be reverted (deleting the override record) to fall back to the base template. | Items | Item Page overrides | `items/page-overrides` | Standalone — this is a full feature with several interacting behaviors (auto-enable, toggle semantics, warning modal, revert), comparable in scope to Linear's 994-word `sla.md`; do not split further, the sub-behaviors don't stand alone. |
| 8 | Core fields vs custom fields | The conceptual split: 4 core fields (`name`, `item_id`, `description`, `tags`) are fixed DB columns whose keys can never change; everything else is a custom field stored in `metadata.fields` JSONB under a stable nanoid, which is what makes renaming safe. | Fields | Core fields vs custom fields | `fields/core-vs-custom` | Standalone — the load-bearing mental model for the whole Fields category; short but necessary, plays the same role as Linear's short "Concepts" orientation page. |
| 9 | Custom field types | The six field types offered when creating a custom field: Text (`string`), Number, Date, Yes/No (`boolean`), List (`array`), and UUID (`object`, used for reference fields). Each type gates which options (allowed values, multiple values, reference config) are available. | Fields | Custom field types | `fields/field-types` | Standalone — one page enumerating all six with their gating behavior; the individual types don't each carry enough distinct mechanics to justify six separate pages (Text/Number/Date/Yes-No are just format constraints), so splitting further would undershoot the calibration rather than meet it. |
| 10 | Allowed values | A fixed, editable list of `{value, label, color}` options that turns a Text or List field into a picker. The color on each option is what colors the matching status/tag chip wherever the field is rendered, including the scanned Page — configure the color once, it applies everywhere. | Fields | Allowed values | `fields/allowed-values` | Standalone — meaty, specific mechanism (verified: `ItemHeader.tsx` reads `getFieldValueColor` from field config to color rendered Tags/status chips) that is a natural sibling to, not a duplicate of, "Allow new values". |
| 11 | Allow new values | A per-field toggle (List and, per the UI, Text fields) controlling whether people can add a value not already on the Allowed Values list. When off, both the item form and CSV import reject any value outside the list; when on, a new value typed in the form is auto-registered into the list, and CSV import accepts it without validation error. | Fields | Allow new values | `fields/allow-new-values` | Standalone — the CSV-validation interaction (`csv-row-validation.ts` skips the allowed-values enum check entirely when `allowNewValues === true`) is a specific, non-obvious behavior worth its own page, exactly the kind of narrow-but-real mechanic Linear gives "Priority" (243 words) to. |
| 12 | Multiple values (List fields) | The "Multiple Values" checkbox, only enabled when Field Type is List, that switches the field's UI from single-select to multi-select (MultiSelect vs SingleSelect) and stores an array instead of a single value. | Fields | Multiple values | `fields/multiple-values` | Standalone — small but a real, distinct toggle with its own gating rule (disabled unless type is List) and UI consequence; on the thin side, flag for a merge into "Custom field types" if the draft can't clear ~150 words on its own. |
| 13 | Reference fields | A field (type UUID) that points at another record instead of holding its own value: another Item (scoped to the same Tub or any Tub on the team), a Tub, or a team member. Renders as a dropdown (optionally searchable) and displays the referenced record's name and image rather than a raw ID. | Fields | Reference fields | `fields/reference-fields` | Standalone — genuinely the richest field mechanic in this domain (three reference types × scope rules × searchable toggle × render behavior); comparable in depth to Linear's `issue-relations.md` (412 words). |
| 14 | Field defaults | A Tub-level default value applied when an Item is created with that field left blank; an explicit Item value always wins and is never overwritten retroactively. On the Destination URL field specifically, the default is stamped onto the Item at creation time, so a later change to the Tub default does not retroactively affect existing Items. | Fields | Field defaults | `fields/field-defaults` | Standalone — the destination-URL "stamped at creation, not retroactive" exception is exactly the kind of specific, surprising behavior that earns a field its own page. |
| 15 | Required fields | The "Required" checkbox, enforced identically at item creation, item edit, and CSV import — with one carve-out: a CSV row that's *updating* an existing Item only has required fields enforced for columns actually present in that row, so a partial update can't be rejected over an unrelated required field it never touched. | Fields | Required fields | `fields/required-fields` | Standalone — the partial-update carve-out for CSV is real, non-obvious behavior distinct from "Allowed values" or "Allow new values". |
| 16 | Creating a custom field | The task of adding a new field: type a display label, get an auto-generated snake_case key (editable), pick a type, and the field is created with a stable nanoid ID for storage. | Fields | Creating a custom field | `fields/creating-a-field` | Standalone — task-shaped page (the "how", as opposed to the conceptual pages above); folds in field-key validation rules (length, format, reserved words, uniqueness) rather than giving those their own page, since they're only ever encountered during creation/renaming. |
| 17 | Renaming a field | Changing a custom field's key and/or label after creation. Safe because the underlying nanoid storage ID never changes — only custom fields with an assigned ID can be renamed this way; core fields (fixed DB columns) can never be renamed. Renaming warns that page-editor property bindings referencing the old key will be auto-updated on save. | Fields | Renaming a field | `fields/renaming-a-field` | Standalone — the "why renaming is safe" mechanic (stable ID vs human-readable key) is a distinct, important concept that deserves explaining on its own rather than as a footnote. |
| 18 | Deleting and disabling fields | Two different removal behaviors: a core field can only be disabled (hidden, re-enable anytime, data untouched) — never deleted; a custom field can be permanently deleted, which warns that Page templates/Destinations referencing it will show broken bindings and its stored data becomes inaccessible. | Fields | Deleting and disabling fields | `fields/deleting-and-disabling` | Standalone — the core-vs-custom asymmetry (disable-only vs. permanent-delete-with-warning) is specific enough to warrant its own page rather than a bullet inside field creation. |
| 19 | Importing Items from CSV | Uploading a CSV to bulk create/update Items in a Tub: each row is create-or-update by matching `id`; every row is validated against the Tub's field config (unknown columns, required fields, allowed-values enums honoring Allow New Values, Item ID pattern) and bad rows are rejected individually while good rows still import; a dry-run mode previews the exact create/update/reject counts before committing. Limits: 10 MB / 10,000 rows. | Import & Export | Importing Items from CSV | `import-export/importing-items` | Standalone — this is the general Item CSV import, explicitly distinct from the print-batch CSV flow (which produces/tracks Media, not Items); substantial, task-shaped content (upload → dry-run preview → per-row error report → commit). |
| 20 | Exporting Items to CSV | Downloading a Tub's Items as CSV, either as only the columns currently visible in the table or as every field (a full backup export), optionally scoped by the same search/filter/sort applied to the on-screen list. Array fields (like Tags) are joined with `; ` in the exported cell. | Import & Export | Exporting Items to CSV | `import-export/exporting-items` | Standalone — distinct concern from import (a download, not an upload) with its own real options (visible-columns vs. full export, filter/search/sort scoping) that clear the atomicity bar on their own. |

## Notes for the drafting phase

- **Field configuration is edited at the Tub level, documented under Items/Fields.** The
  "Fields" tab lives in Tub settings, so there's a real question of whether the "Fields"
  category above should instead be a subsection of a "Tubs" nav category, or its own
  top-level category as proposed. Flagged as an open question below — whichever domain pass
  owns "Tubs" will hit the same field-config code and should not duplicate this table.
- **System fields** (`id`, `tub_id`, `created_at`, `updated_at`, `destination_config`) were
  deliberately *not* given individual pages — they're internal/infrastructure fields with no
  standalone user-facing behavior worth a page. `image` was the one exception (row 5) because
  it has real cross-feature behavior (reference-field previews, Page rendering). If drafting
  finds "Item image" too thin once written, fold it into row 1 ("What is an Item?").
- **`destination_url` is deliberately excluded** from this inventory even though it lives in
  `fieldConfig.fields` — per the code comments it's "not a user-configurable field," managed
  by the Destination tab of the Page Editor, and belongs in a Pages/Destinations domain pass,
  not Items.
- **The print-batch CSV flow (`export-print-csv`, `access-links/export-print-csv`) is out of
  scope for this inventory** — it exports Links/Media for printing, not Items, and belongs to
  a Media/Print-batches domain pass. Rows 19–20 above cover only the general Item CSV
  read/write at `/api/tubs/[id]/items/{import-csv,export-csv}`.
- **The default metadata field library** (`item_number`, `serial_number`, `category`, `type`,
  `subtype`, `status`, `location`, `owner`, `equipment_manager`, `notes`,
  `manufactured_date`, `parent_item` in `DEFAULT_FIELD_DEFINITIONS`) are canned starter fields
  offered in the "Add More Fields" picker — not distinct product concepts. They should be
  *mentioned* as examples inside row 9 ("Custom field types") or row 16 ("Creating a custom
  field") rather than given individual pages; doing otherwise would overshoot the Linear
  calibration (Linear doesn't have a page per possible custom field either).
- **Field order** (drag-to-reorder the field chips, backed by `fieldConfig.fieldOrder`) was
  considered and rejected as a standalone page — too thin on its own. Fold a short mention
  into row 16 ("Creating a custom field") or row 8 (core-vs-custom overview).
- Word-count sanity check against the Linear calibration: the thinnest rows here (Item image,
  Multiple values) are flagged explicitly as merge-candidates if drafting can't clear ~150
  words of genuinely distinct content; everything else has enough verified, specific
  mechanism (uniqueness constraints, color-driven rendering, CSV validation carve-outs,
  stamped-vs-retroactive defaults) to comfortably clear the 243–994 word range Linear itself
  spans.
