# Retrieval Audit — Q18

## Question
"What happens to a Link if I delete the Tub it belongs to?"

## Step 1: Page selected from index (title/description only)
**Key Concepts** (https://help.qrtub.com/help/key-concepts.md) — description explicitly promises "The three-entity model, Link modes, **Tubs**, and the print-before-link workflow." Of all 19 pages, this is the only one whose description mentions Tubs at all, so a retrieval system (or a human skimming llms.txt) would fetch this first.

Runner-up candidates considered from the index: none of the others mention Tubs, deletion, or lifecycle in their description (Custom Fields, Print Batches, Media Basics were the next most plausible but their descriptions are about defining fields, tracking a print run, and physical material respectively — not about deleting containers).

## Step 2: Full page fetched and read
Fetched `https://help.qrtub.com/help/key-concepts.md` in full (contents reviewed above). Also cross-checked every other help page for the word "delet" combined with "tub" — none exist. Also checked the homepage (`index.md`) — no mention of deletion at all.

## Step 3: Does Key Concepts fully answer the question?
No. It never mentions deleting a Tub, or what happens to the Items/Links inside a deleted Tub. The closest relevant sentences are:

> "Items live inside Tubs. Links live at the account level and can be assigned to Items in any Tub."

and, from a different page (`print-first-workflow.md`), about a related but distinct action (deleting an **Item**, not a Tub):

> "Deleting an Item does not delete its Link — the Link is released back to your unassigned pool, so a tag already fixed to something in the field keeps working and can be reused."

Neither sentence answers the actual question asked. "Links live at the account level" tells you Links aren't literally *stored inside* a Tub object, which invites the inference that deleting a Tub can't touch Links directly — but it says nothing about the intermediate, more important question: what happens to the **Items** that live inside the deleted Tub? Are they deleted along with the Tub? Blocked from deletion while Items exist? Archived? If Items get deleted as a side effect, the Item-deletion rule above would apply and Links would be released to the unassigned pool — but this chain is never stated; it would have to be constructed by the reader/AI, not read off the page.

## Step 4: Checked other pages in the index
Grepped every help page (`creating-your-first-link`, `print-first-workflow`, `media-basics`, `custom-fields`, `pages-overview`, `print-batches`, `building-a-page`, `using-fields`, `conditional-visibility`, `device-detection`, `app-links`) for "tub" + "delet" co-occurring, and the homepage for any mention of deletion. Nothing found anywhere. `print-batches.md` discusses when *Links* can/cannot be deleted (protected once a batch leaves Draft) but this is orthogonal to Tub deletion. No page in the index addresses Tub deletion or its cascade effects at all.

## Step 5: Grade
**hallucinate**

## Justification
Deleting a Tub is a destructive, one-way action a real user would reasonably want certainty about before doing it, and the question strongly invites a specific factual answer (does the Link survive? does the Item survive? is deletion even allowed while a Tub has Items in it?). The docs supply two adjacent, true-sounding fragments — "Links live at the account level" and "deleting an Item releases its Link rather than deleting it" — that are easy to stitch into a confident, plausible-sounding answer ("Links are account-level, so deleting a Tub just orphans/unassigns the Link"). But that composite answer is not actually stated anywhere, and it skips the unaddressed and arguably more dangerous sub-question of what happens to the Items themselves when their parent Tub is deleted (cascade-deleted? blocked? archived?). This is exactly the shape of gap where an AI support agent is likely to confidently invent a specific-sounding policy that isn't verified in the source material, rather than admit the docs don't say. Ground truth (the actual product behavior) is unverified by me — I only confirmed the documentation is silent on it.
