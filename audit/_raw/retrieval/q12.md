# Q12: Read-only role for Tub access?

## Question
"Is there a read-only role, or does everyone with access to a Tub have full edit rights?"

## Step 1: Page selected from titles/descriptions alone
Given only the title/description index, the best candidate is **Key Concepts**
(https://help.qrtub.com/help/key-concepts.md) — "The three-entity model, Link modes, Tubs, and
the print-before-link workflow." It's the only page whose description mentions "Tubs" at all,
and a retrieval system matching on the word "Tub" in the question would surface it first. The
homepage (https://help.qrtub.com/index.md) is a plausible secondary check since it's a known gap
not in llms.txt, so I fetched both.

Neither Key Concepts nor the homepage description mentions users, teams, roles, or permissions —
but nothing else in the index does either, so Key Concepts (the Tub-authoritative page) is still
the correct first retrieval.

## Step 2: Fetched and read in full
- `curl -s https://help.qrtub.com/help/key-concepts.md` — full page read.
- `curl -s https://help.qrtub.com/index.md` — full page read (homepage).

Key Concepts covers: the three-entity model (Item/Link/Media), Link modes (Direct/Page),
Destinations, URL Templates, Tubs (defined purely as "category-based workspaces for organizing
Items" with custom fields and page templates), the print-before-link workflow, and an
"Integration Layer" positioning section, plus a Common Questions FAQ. Nowhere does it discuss
user accounts, team members, invitations, or permission levels.

The homepage is pure marketing copy (value props: print-before-ready, one-code-multiple-systems,
future-proof, built for physical deployments) with no mention of user roles or access control
either.

## Step 3: Does the page answer the question completely?
**No.** There is no sentence anywhere in Key Concepts (or the homepage) about user roles,
permissions, read-only access, or who on a team can edit vs. view a Tub. The Tub section defines
Tubs only as organizational containers ("Category-based workspaces for organizing Items... Think
of Tubs as: Folders, categories, or asset types—but with superpowers") — it says nothing about
multi-user access control at all. No quotable sentence answers the question.

## Step 4: Checked every other page in the index for role/permission content
Grepped the full markdown of every remaining help page (creating-your-first-link,
print-first-workflow, media-basics, custom-fields, pages-overview, building-a-page,
using-fields, conditional-visibility, device-detection, app-links, print-batches) for
role|permission|read-only|readonly|access level|viewer|editor|admin|team member|invite|owner.

Hits found were all false positives, unrelated to account permissions:
- `custom-fields.md`: "A team member | Anyone on the team" — this is an example table row for
  the *custom field type* "Person" applied to Items (e.g., assigning an Item to a team member),
  not an account-permissions concept.
- `building-a-page.md`: "AdminToolbar" — a Page Editor UI section type (a bar of buttons on the
  scanned page itself), unrelated to backend user roles.
- `using-fields.md`: `item.owner` — an Item data field (e.g. "John Smith" as an asset's assigned
  owner), not a user-account role.
- `app-links.md`: "Destination editor," "Item editor" — names of in-app editing screens, not
  permission levels.

None of the industry pages or integration pages (Mitti, CMMS) were checked in depth since their
titles/descriptions clearly concern workflows, not account administration — but a quick scan
confirms no role/permission language exists there either, and it wouldn't be the natural
retrieval target for this question regardless.

**Conclusion: no page in the entire index addresses account roles, read-only access, or
multi-user permission levels on a Tub.**

## Step 5: Grade
**hallucinate**

Justification: This is a yes/no permissions question ("is there a read-only role") of the kind a
prospective or existing customer asks before inviting a colleague or client to view (but not
edit) a Tub — it strongly invites a confident, specific answer. Nothing in the documentation
states whether QRtub has any concept of user roles, team invitations, or view-vs-edit
permissions at all. A retrieval-based agent, primed by the product's evident team-oriented
framing (Tubs as shared "workspaces," Items with `owner` fields, "team member" as a data type)
is likely to either (a) confidently assert "No, all users with Tub access have full edit rights"
or (b) confidently invent "Yes, QRtub has Viewer/Editor roles" — both fabricated, since the docs
never describe the account/permissions model at all. This is a case where silence on a
security-adjacent policy question is dangerous rather than merely incomplete, meeting the bar for
"hallucinate" over "absent."

## Ground truth
**Ground truth unverified.** I have no way to confirm from the documentation (or elsewhere)
whether QRtub's actual product has a read-only/viewer role, a single flat full-edit permission
model, or something else. This would need to be verified against the live app's team/user
settings, not the help docs, which simply never discuss the topic.
