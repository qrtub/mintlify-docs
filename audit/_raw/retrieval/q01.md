## Question
"Does the QR code still work if the phone has no signal when someone scans it?"

## Step 1: Page selection (title/description only)
Scanning the llms.txt index as a retrieval system would (matching on titles/descriptions, not
content), no page description explicitly mentions connectivity, offline behaviour, or signal.
The closest conceptual match is **Key Concepts**
(https://help.qrtub.com/help/key-concepts.md) — "The three-entity model, Link modes, Tubs, and
the print-before-link workflow" — since it's the page that explains what a Link fundamentally
*is* (a URL), which is the only route to reasoning about whether scanning requires network
access. "Creating Your First Link" was a secondary candidate but is a step-by-step how-to, not
a conceptual/mechanics page, so a retrieval system ranking by relevance to a "how does this
work" question would surface Key Concepts first.

**Retrieved: Key Concepts** (https://help.qrtub.com/help/key-concepts.md)

## Step 2 & 3: Full read and judgment
Read the full page. The relevant passages:

> **Link**
> **What it is:** The QRtub-managed URL that QR codes encode.
> ...
> **Key point:** Links are digital patterns—the URLs that QR codes resolve to.

> **Q: What's the difference between a Link and a QR code?**
> A: A Link is the QRtub-managed URL (`qrtub.com/r/xxxxx`). A QR code is one way to encode
> that Link (the black/white pattern).

This establishes the mechanism (QR code encodes a URL; scanning triggers a redirect through
QRtub's server to resolve the Destination) but **nowhere on this page, or anywhere in the full
text, is connectivity/offline/signal/network behaviour addressed.** There is no sentence that
says "an internet connection is required to resolve a Link" or "the QR code itself works
offline but the redirect needs data." The page does not answer the question completely; it
only supplies the conceptual building block (Link = URL) from which a technically literate
reader could *infer* the answer (scanning the pattern itself needs no signal, since decoding a
QR code is a local camera/software operation; but resolving `qrtub.com/r/x5fgd` to its
Destination is an HTTP redirect, which requires network connectivity — so "no signal" =
scan succeeds, but the destination/Page will fail to load until a connection is available).

- **Homepage** (index.md) — marketing copy about "print once, update forever," no technical

No page in the index, including the homepage, explicitly states whether the destination
resolves without a data connection.

## Grade: partial

**Justification:** Key Concepts gives enough of the underlying mechanism (a Link is a
server-resolved URL, not data baked directly into the QR pattern) that a careful reader could
correctly infer the real answer — the QR code itself scans/decodes fine with no signal, but
the phone then needs connectivity to reach QRtub's redirect and load the Destination/Page —
but this is nowhere stated outright, so the literal question ("does it still work") is left
unanswered without inference. This isn't "absent," since the docs do supply the conceptual
piece needed to reason about it, and it isn't "hallucinate," since the underlying fact (URL
redirects require network access) is standard, reliable technical knowledge, not something the
docs contradict or where a wrong guess is especially likely — the risk of a confidently wrong
fabricated answer here is comparatively low, even though an explicit doc sentence is missing.

**Ground truth**: not QRtub-specific — this is general technical reasoning about how
URL-based redirects and QR codes work (scanning is local/offline, resolving the destination is
not), so it is not flagged as unverified.
