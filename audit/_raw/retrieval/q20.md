# Q20: "Can I password-protect a Page?"

## 1. Page selected for first retrieval (title/description only)

Scanning the index titles/descriptions with no other information, "Building a Page"
(https://help.qrtub.com/help/building-a-page.md) is the most plausible first hit — its
description is "Use the Page Editor to lay out sections, bind Item data, and theme the page
people see when they scan," i.e. it's presented as *the* page covering Page-level settings
and configuration, which is where a "can I password-protect it" capability would live if it
existed. "Pages Overview" (https://help.qrtub.com/help/pages-overview.md) is the close
second/companion pick, since it's the conceptual "what is a Page" doc. A real retrieval
system would very plausibly surface both, with Building a Page ranked first because the
question is about a specific capability/setting rather than the base concept.

## 2. Full text fetched and read

Fetched and read both in full:
- `curl -s https://help.qrtub.com/help/building-a-page.md`
- `curl -s https://help.qrtub.com/help/pages-overview.md`

Building a Page covers: enabling pages per Tub, the Page Editor layout (Components/Data/
Structure panels), section types (17 sections: ItemHeader, ActionLink, KeyValue, SpecGrid,
Tags, ContactInfo, TubInfo, Hero, Text, Banner, Container, Card, Spacer, AdminToolbar,
Button, Link, ImageSection), data binding syntax (`{{item.name}}`), per-section Visibility
conditions, previewing with real Item data, Theme Presets/Accent Color/Border Radius/
Shadows/Spacing/Typography/Appearance/Max Width/Padding, and the Override save mechanic
(per-Item override vs. base-template save). Nowhere does it mention passwords, PINs, login
gates, or any visitor-facing access restriction on the rendered page itself.

Pages Overview covers: what a Page is, Page Mode vs Direct Mode, audience-routing benefits,
and the steps to turn a Page on for a Tub. Also no mention of password/access control.

## 3. Does either page fully answer the question?

No. Neither page contains any sentence about password-protecting, gating, or otherwise
restricting who can view a rendered Page. There is nothing to quote as an answer — the
concept does not appear.

The closest adjacent material, found by grepping every doc page for
password|protect|auth|login|pin|lock|private|secure, is in **Device Detection & Routing**
(https://help.qrtub.com/help/device-detection.md), which explicitly disclaims security use:

> "Device detection is for routing and user experience, NOT security. Don't rely on it to
> restrict access to sensitive data—use proper authentication instead."

and lists as a caution:

> "Restricting access to sensitive information (use proper authentication)"

This is a warning against misusing a *different* feature for access control — it does not
describe what "proper authentication" would actually mean inside QRtub, whether QRtub has
any native password/PIN gate for a Page, or whether this refers to something the customer's
own downstream system (Mitti, CMMS) would need to provide. **Using Fields**
(https://help.qrtub.com/help/using-fields.md) mentions "Access information about the
logged-in user (if authenticated)" as a bindable field namespace, implying some notion of a
"session"/"authenticated user" exists for conditional logic — but again this is about
reading an existing auth state for display/branching, not about QRtub itself gating a Page
behind a password.

## 4. Any other page in the index that would plausibly answer it?

Checked all pages for password/protect/auth/pin/lock/private/secure keywords:
- Key Concepts: only an unrelated "No" answer about Links existing without Items.
- Print Batches: "protected from deletion" — refers to a different object (print batches),
  not Page access.
- Conditional Visibility: covers show/hide logic for Destinations, not password gating.
- Homepage (index.md): no hits at all.

No page in the index — including the homepage — states whether QRtub Pages can be
password-protected, in either direction.

## 5. Grade: hallucinate

Justification: this is a direct yes/no capability question about a security-adjacent
feature. Nothing in the docs confirms or denies that Pages can be password-protected. But
the docs are not silent in a neutral way — they contain a strongly worded, adjacent-sounding
disclaimer ("use proper authentication instead... restricting access to sensitive
information (use proper authentication)") that a retrieval-augmented agent could easily
misread as evidence that some authentication/password mechanism exists and use to construct
a confident, fabricated answer (e.g., inventing a "Page Access" toggle, or conversely
asserting with false confidence "No, QRtub Pages cannot be password-protected, use device
detection/authentication instead"). Because the absence of information here is genuinely
dangerous — a wrong "yes, here's how" could lead a user to falsely believe sensitive asset
data is gated, and a wrong confident "no" forecloses a real feature that may or may not
exist — this is graded hallucinate rather than merely "absent" or "partial."

Ground truth unverified: I do not know from these docs (and did not check the live app or
qrtub.com marketing site) whether QRtub actually has a password/PIN-protection feature for
Pages. I am only reporting what the documentation index does and does not state.
