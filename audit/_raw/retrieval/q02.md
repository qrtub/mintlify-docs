# Retrieval Audit — Q02

## Question
"What happens when someone scans a QR code whose Item has been deleted?"

## Step 1 — Page picked from titles/descriptions alone
Scanning the index without reading any full page, the strongest title/description match is:

**Key Concepts** (https://help.qrtub.com/help/key-concepts.md) — "The three-entity model, Link
modes, Tubs, and the print-before-link workflow."

Rationale for picking this first: the question is fundamentally about the relationship
between an Item and a Link (does deleting one destroy the other, and what does the Link do on
scan afterward). "Key Concepts" is the only page whose description explicitly promises to
explain the Item/Link/Tub model and the "print-before-link" relationship, so a title-based
retrieval pass would surface it ahead of anything else. "The Print-First Workflow" is a
plausible second guess (its description mentions "apply them as gear arrives... connect them
when you are ready", which is adjacent but reads as being about the *pre*-connection state,
not deletion), but on description text alone "Key Concepts" ranks higher for a question that
uses the words "Item," "deleted," and "QR code" together.

## Step 2 — Fetched and read in full
`curl -s https://help.qrtub.com/help/key-concepts.md`

Read in full (three-entity model, Link modes, Destinations, URL Templates, Tubs,
print-before-link workflow, "Update Without Reprinting," Integration Layer, and the "Common
Questions" FAQ block).

## Step 3 — Does Key Concepts answer the question completely?

No. The closest material is:

- The worked example: "Each entity has its own lifecycle. The excavator might be sold. The
  Link persists and can be reassigned. The metal plaque might outlast the excavator and get
  moved to new equipment." — this is about Media outliving an Item, not about what a scan
  shows once the Item record itself is deleted.
- FAQ: "Q: Do I need Items to use Links? A: No. Links can exist without Items (useful for
  simple redirects)." — establishes Links can be Item-less in general, but never states what
  happens to an *existing* Link when its Item is deleted, nor what a scanner sees.
- FAQ: "Q: What happens to my scan data if I replace damaged Media? A: ... The Item connection
  stays intact..." — answers a different, adjacent question (Media replacement), not Item
  deletion.

Nothing on this page states what becomes of the Link when the Item is deleted, and nothing
describes the scan-time behavior (error page vs. neutral page vs. still redirecting). Grade
for this page alone: does not answer the question; requires inference, and the inference
would likely be wrong or unconfident.

## Step 4 — Does any other indexed page answer it?

Yes — **The Print-First Workflow**
(https://help.qrtub.com/help/print-first-workflow.md) answers it directly and completely, in
two parts:

1. On scanning an unconnected/unassigned Link:
   > "an unconnected code does not 404... Anyone else gets a neutral branded page rather than
   > an error."

2. On what deleting an Item does to its Link (fetched directly, confirmed present verbatim on
   the page):
   > "Deleting an Item does not delete its Link — the Link is released back to your
   > unassigned pool, so a tag already fixed to something in the field keeps working and can
   > be reused."

Put together, these two sentences on the *same* page fully answer the user's question: when
an Item is deleted, its Link is not deleted — it reverts to the "unassigned" pool, which per
this page's own description of unassigned-code scan behavior means a scanner sees a neutral
branded page, not an error/404. The page even cross-references Key Concepts at the end of
that section ("See Key Concepts"), which is backwards from what a reader would need — Key
Concepts does not actually contain this fact, so the cross-reference is a minor documentation
gap in its own right.

No other page in the index (Custom Fields, Pages Overview, Print Batches, Media Basics, the
industry pages, or the integration pages) contains any statement about Item deletion or its
effect on scan behavior. (Print Batches has an adjacent but distinct rule: links inside a
non-draft batch cannot be deleted at all, which is about protecting the *Link* from deletion,
not about deleting the *Item*.)

## Grade: partial

Justification: the page a title-based retrieval pass would surface first (Key Concepts)
does not contain the answer and only offers adjacent, inference-inviting material (Media
outliving an Item, Links existing without Items) — but the actual, complete answer does exist
verbatim on another indexed page (The Print-First Workflow), so this is not "absent," and
because the true fact is documented and discoverable, a careful retrieval system checking
more than one page would not need to invent anything, which keeps this out of "hallucinate."
The risk is real, though: a naive single-page-fetch agent that stops at Key Concepts (the
title-plausible first guess) would very likely have to guess/infer an answer about
error-page vs. redirect behavior — this is exactly the kind of case that tips into
"hallucinate" if the agent doesn't chase the cross-reference or search further.

Ground truth: verified from the docs themselves (print-first-workflow.md states it
explicitly), not inferred — no "ground truth unverified" caveat needed for the underlying
product behavior itself, only for how discoverable it is via naive retrieval.
