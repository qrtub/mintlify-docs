# Q37: "What happens if my Mitti template ID changes after I've already deployed 500 QR codes using it?"

## 1. Page I would retrieve first

Based on title/description matching alone, **Mitti (formerly SafetyCulture / iAuditor)**
(`https://help.qrtub.com/integrations/safetyculture.md`) is the obvious first pick — the question
names "Mitti" and "template ID" directly, and this is the only page in the index whose description
explicitly mentions Mitti and inspection templates ("Open Mitti inspections straight from a scan,
pre-filled with the item's data").

## 2. Full read of that page

Fetched via `curl -s https://help.qrtub.com/integrations/safetyculture.md`. Full content reviewed.

Relevant passages:

> **Getting Your Template ID**
> Before setting up deep links, you'll need your Mitti Template ID: ... Copy the Template ID from
> the URL ... Example: `template_fcbc86fd41a74180921347e4be53bdf2`

> **Using QRtub URL Templates**
> Use QRtub's URL Template feature to automatically insert template IDs from your Item data:
> **Destination URL:** `iauditor://template/new_audit/{{item.templateID}}`
> **Why this matters for bulk deployment:** Configure the Destination once with a template
> placeholder. Each Item in your Tub can have a different `templateID` field value... One
> Destination configuration serves all equipment types, with each QR code routing to its specific
> inspection template automatically.

> **Bulk deployment benefit:** Configure this URL once. Deploy to 500 pieces of equipment. Each
> scan substitutes that Item's own asset ID into the link... No manual setup per Item.

This is all about *initial setup* of a Mitti Destination at deployment time, using either a
literal hardcoded template ID or a `{{item.templateID}}` field binding. **Nowhere on this page
does it discuss what happens if the underlying Mitti template ID subsequently changes** —
whether QRtub is even aware of the change, whether existing deployed codes silently start
resolving to a broken/wrong template until someone updates something, or what the update
procedure is for 500 already-created Items (one shared Destination edit vs. 500 individual field
edits, depending on how it was originally configured). The Troubleshooting section only covers
"Template ID format incorrect" as an initial-setup issue, not an after-the-fact ID change.

**Verdict: this page alone does not answer the question.**

## 3. Checking other pages — Key Concepts

**Key Concepts** (`https://help.qrtub.com/help/key-concepts.md`) contains the general architecture
answer that is directly on point, in its "Update Without Reprinting" section:

> **The core benefit:** Change where your QR codes point at any time without touching the physical
> codes.
>
> **Example:** 500 equipment QR codes point to "System A" for inspections. Two years later, you
> switch to "System B." With traditional QR codes, you reprint 500 codes. With QRtub, you update
> 500 Destinations. Physical codes unchanged.

And from the FAQ:

> **Q: Why can't I just use a regular QR code generator?**
> A: Regular generators hardcode URLs into QR codes. Once printed, they can't be changed. QRtub
> decouples the physical code from its Destination, enabling updates without reprinting.

Combined with the Mitti page's `{{item.templateID}}` field-binding mechanism, a fairly confident
synthesized answer emerges: nothing breaks the physical QR codes themselves (they encode a QRtub
Link, not the raw Mitti template ID), and no reprinting is required — you just update either (a)
the Destination URL, if the template ID was hardcoded directly into it, or (b) the `templateID`
custom field value(s) on the affected Items, if it was field-bound. Until that update is made,
scans presumably continue resolving to the *old* (now-wrong) template ID.

However, this synthesis requires combining two pages and still leaves real gaps the docs never
state explicitly:
- Whether QRtub has any bulk-edit tool for updating a custom field's value across many
  already-existing Items at once (vs. editing 500 Items one at a time), which matters a lot if the
  ID was field-bound rather than hardcoded in a single shared Destination.
- What actually happens to a scan in the interim — does it silently 404/error in Mitti, or does
  Mitti handle unknown template IDs gracefully? (This is Mitti's behavior, outside QRtub's docs
  entirely.)
- Whether a hardcoded ID lives in one Destination (shared across many Items via a Page template)
  or must be repeated per Item — the answer depends on setup choices not fully spelled out for
  this exact scenario.

## 4. Grade

**partial**

The Mitti integration page (the natural first retrieval target) covers only initial setup of
template IDs and says nothing about what happens if the ID changes post-deployment. The Key
Concepts page supplies the general "no reprinting needed, just update the Destination/data" answer
that plausibly extends to this scenario, but neither page — nor any other in the index — states
this explicitly for the Mitti-template-ID-change case, nor addresses bulk-updating field values
across many already-existing Items or the interim broken-link behavior. A real retrieval agent
would likely need to infer the answer by combining two pages, and would still be guessing at the
bulk-edit mechanics and the interim failure mode.

Ground truth on bulk-editing custom field values across many existing Items, and on Mitti's
behavior when given a stale/unknown template ID, is **unverified** from the docs alone.
