# Retrieval Audit — Q28

## Question
"Is there a QRtub mobile app, or is it web-only?"

## Step 1: Page chosen from index (title/description only)
Scanning the index, no page title says "mobile app" outright, but two are the most plausible candidates a retrieval system (or a human skimming titles) would reach for:

1. **Homepage** (`https://help.qrtub.com/index.md`) — general "what is QRtub" overview, a natural first stop for a product-scope question like this.
2. **App Links & Fallback URLs** (`https://help.qrtub.com/help/app-links.md`) — description: "Use deep links to open mobile apps directly, with automatic fallback when the app isn't installed." The word "app" in the title and "mobile apps" in the description make this a strong lexical match for a query containing "mobile app," even though a careful reader would notice the description says *open mobile apps* (plural, third-party), not *QRtub's own app*.

Given retrieval is usually driven by keyword/embedding similarity rather than careful semantic parsing, **App Links & Fallback URLs** is the page I'd expect a naive retrieval system to surface first for this query, with the homepage as a secondary/fallback pull. I checked both, plus Key Concepts (the architecture-overview page) for completeness.

## Step 2 & 3: Content and whether it answers the question

**Homepage** (`index.md`) — no mention of a mobile app, app store, or "web-only" framing at all. It talks about "Deploy QR codes," "Update Destinations," "Core features available today" (Bulk Link generation, Pages with multiple destinations, Print-before-link workflow, URL Templates). Nothing addresses whether QRtub itself has a companion mobile app.

**App Links & Fallback URLs** (`app-links.md`) — on inspection, this page is entirely about QRtub *Destinations* linking out to **other** installed apps (Mitti/SafetyCulture, Spotify, a custom CMMS app) via custom URL schemes, with a fallback when *that third-party app* isn't installed:

> "QRtub Destinations support app deep links — special URLs that open a mobile app directly to a specific screen. When someone scans and the app isn't installed, QRtub automatically falls back to a URL you specify..."
>
> "`iauditor://template/new_audit/<template_id>` — opens Mitti (formerly SafetyCulture) to a specific template"
> "`myapp://asset/EXC-203` — opens a custom app to an asset record"

This page never states or implies that QRtub itself ships a mobile app. It does not answer "is there a QRtub mobile app" — it's about deep-linking to *other* apps from a scanned QR code. A careless reading of the title, though, could easily lead an agent to answer "yes, QRtub has app functionality" by conflating "QRtub supports app links" with "QRtub has an app."

**Key Concepts** (`key-concepts.md`) — describes Page Mode as opening "a Page—a **mobile-friendly landing page**" and frames QRtub as "a connection layer between your physical items and your digital systems" that is explicitly **not** asset/inspection/maintenance/compliance software itself. This is suggestive (QRtub renders pages in a mobile browser, not a native app) but never states "QRtub is web-only" or "there is no QRtub app" in so many words.

## Step 4: Any other page that could answer it?
No page in the index — including Creating Your First Link, Pages Overview, Building a Page, Print Batches, or any industry/integration page — makes any explicit statement about a QRtub-branded mobile app existing or not existing. The closest circumstantial evidence across the whole doc set is the repeated framing of Links resolving to "mobile-friendly" web Pages/URLs, and the complete absence of any "download our app" call-to-action anywhere (homepage, get-started section, industry pages). This is suggestive but not a direct statement.

## Step 5: Grade
**hallucinate**

Justification: No page anywhere in the docs (or the homepage) states whether QRtub has a native mobile app or is web-only. The one page whose title/description most closely lexically matches "mobile app" (App Links & Fallback URLs) is actually about linking OUT to third-party apps like Mitti — a strong bait for a retrieval system or reader to conflate "QRtub supports app-link Destinations" with "QRtub itself has an app," producing a confident but unverifiable/likely-wrong answer. Meanwhile the real signal (Pages are web-rendered, "mobile-friendly landing page," no app-store CTA anywhere) only supports an inference, never a direct statement, so an agent forced to answer yes/no is filling a real gap with invented certainty either way it goes.

## Ground truth
Ground truth unverified from the documentation set. Circumstantial evidence (QR codes resolve to web Links/Pages, "mobile-friendly landing page" language, no app-store mention anywhere in docs or homepage, Key Concepts explicitly framing QRtub as a web-based "connection layer" rather than a piece of software you install) strongly suggests QRtub is web-only with no native app, but this is inference from architecture description, not a documented fact.
